# ADR 0002: 練習ファイルは名前付きモジュールにし、自分の main でテストを持つ

- Status: Accepted
- Date: 2026-08-24

## Context

3つの問題が同じ根から出ていた。

1. **テストが無い** (issue #4)。動作確認は `print` を目視するだけで、実際にこれで
   「末尾の区切りで最後の空フィールドが落ちる」バグを見逃していた。露見したのは
   `""` / `"a;"` / `";"` / `"a;;b"` を機械的に流したときだった。
2. **`module` 宣言が無く、ファイル間で import できない** (issue #5)。全ファイルが
   暗黙の `module Main` になっていた。ベンチを取るのに `module` ヘッダを付けた
   コピーを作る必要があった。
3. **`make check` が `ghci` 頼みだった**。`main` を持たないファイルを `ghc` に渡すと
   型検査自体は通るのに `The IO action 'main' is not defined` で落ちるため、
   `ghci -Wall -Werror -e 'return ()'` という回り道をしていた。

調べたところ、`module` ヘッダと `main` はそれぞれ独立に効くと分かった。

| 問題 | `module` ヘッダ | `main` |
| --- | --- | --- |
| import できない | 解決 | — |
| `make build` の対象外 | — | 解決 (`-main-is` が要る) |
| `make check` が `ghci` 頼み | 解決 | — |
| テストが無い | — | 解決 (`main` = テストランナー) |

さらに `ghc -main-is <Module>` を使えば **`Main` という名前でないモジュールからも
実行ファイルを作れる**。つまり「名前付きモジュールにする」ことと「実行できる」ことは
両立し、トレードオフではない。

## Decision

練習ファイルは `Prac_NN_Topic.hs` とし、

- `module Prac_NN_Topic where` を付ける
- **自分の `main` を持ち、それが自分のテストを走らせる**
- テストヘルパは `TestKit.hs` を import する

`make test` が `$(wildcard Prac_*.hs)` を拾い、`ghc -main-is Prac_NN_Topic` で
各々をビルドして実行する。`make check` は素の `ghc -fno-code -Wall -Werror` に戻した。
pre-commit hook は `fmt-check` / `check` / `test` の順に回す。

テストは表駆動で、期待値を書き下すケースに加えて**不変条件**も書く。
Prac_01 では「Span で切り出して区切りで繋ぎ直すと元の入力に戻る」を検査している。
不変条件は入力を足してもタダで効くので、表より安く広い範囲を守れる。

## Consequences

### 得られるもの

- **新しいトピックを足すのに登録作業が要らない。** ファイルを置けば `make test` が拾う。
  中央のテスト一覧に登録する形にすると、このリポジトリの最優先事項
  (今試したいことを素早く試せること) と摩擦する
- `make check` が素直な `ghc` に戻った
- スクラッチ同士で import できるようになった
- テストが実装の隣にあるので「何を確かめたのか」が残る

### 支払う代償

- **実装とテストが同じファイルに同居する。** 練習用途では利点でもあるが、
  ファイルは確実に長くなる
- **ファイルが増えると `make test` のビルドが線形に増える。**
  `$(BUILD)/test-%: %.hs` の形にしてあるので変更したものだけ再ビルドされるが、
  各々が独立した実行ファイルになるためリンクの回数は減らせない
- **`-main-is` は知らないと不思議に見える。** `Main` でないモジュールから
  実行ファイルが出てくる理由が Makefile を読まないと分からない
- **`TestKit.hs` は最小限。** 表駆動の比較しかできず、QuickCheck のような
  性質検査や shrink は無い。必要になったら `flake.nix` に `p.QuickCheck` を
  明示して足すこと (宣言せずに推移閉包から拾わない、ADR 0001 参照)

## Alternatives considered

- **`Tests.hs` にテストを集約する**: 本体は綺麗になるが、ファイルを足すたびに
  `Tests.hs` への登録が要る。登録作業を増やす設計は取らない。
- **hspec / tasty を入れる**: 本筋だが、Cabal project を作らない方針 (ADR 0001) だと
  テストランナーの導入が重い。表駆動で足りている間は入れない。
- **`module` ヘッダだけ付けて `main` は入れない**: import と `make check` は解決するが
  テストが無いままになる。3つの問題のうち1つが残る。
