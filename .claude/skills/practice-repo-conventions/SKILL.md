# Haskell 練習リポジトリの作業方針

## 書いたコードは写経の題材になる

本人は Claude が書いたコードを**写経して理解する**学習方法を取っている
(2026-08-24 に明言)。したがって:

- **頼まれたら普通に書く。** 「学習のために渡さない」といった遠慮は不要
- ただし**お手本として通用する品質**で書くこと。ここが普通の実装と違う点

お手本であるために意識すること:

- 素直で、その言語らしい書き方をする。技巧に寄らない
- **なぜそう書くのかがコードから読み取れるようにする。**
  型の選択や不変条件は haddock に書く。「何をしているか」ではなく「なぜか」
- 一足飛びに凝った実装をしない。段階が追える形にする
- 命名で意図を伝える (`anchor` / `cursor` のように役割が分かる名前)

## 最優先事項

**今試したいことを素早く試せること。** 既存の運用・規約・ビルド構成を壊してよい。
後方互換を理由に劣る設計を選ばない。より良い形があれば移行を提案する。

このリポジトリは練習用で、安定運用そのものには価値が無い。摩擦を減らすことが目的。
破壊的変更の可否を毎回確認しなくてよいが、**何を壊したかはコミットメッセージに書く**。

この方針から導かれる具体的な判断:

- **新しいトピックを足すときに登録作業が増える設計を避ける。**
  中央の一覧ファイルに登録させる形にしない。ファイルを置けば拾われるようにする
- ツールが `main` を要求する等の理由で回り道が必要になったら、
  回り道を工夫するより**前提のほうを変えられないか**先に考える

## ビルド構成: Cabal project を作らない

依存は `flake.nix` の `haskellPackages.ghcWithPackages (p: [ ... ])` で宣言し、
`ghc` / `ghci` を直接叩く。`*.cabal` / `cabal.project` を作らない。
パッケージを試す手順は「`flake.nix` に1行足す → `direnv reload`」。

理由と代償は `docs/adr/0001-ghc-with-packages-without-cabal.md` に記録済み。
**`.cabal` ファイルの追加を提案しない。** 配布やライブラリ公開の話が出たときだけ再検討する。

### この構成の落とし穴

- **宣言していないパッケージが import できてしまう。**
  `ghcWithPackages` は推移閉包をパッケージ DB に入れ、GHC は既定で全部 expose する。
  使うパッケージは必ず `flake.nix` に明示すること (`word8` が実例)
- **警告フラグが二重管理。** `Makefile` の `WARNFLAGS` と `hie.yaml` の
  `cradle.arguments` は手で同期する。片方を変えたら両方直す。
  `hie.yaml` が無いと HLS の診断から `-Wall` が丸ごと消える (型エラーは出るので気付きにくい)

## ファイルの規約

- 練習ファイルは `Prac_NN_Topic.hs`。`module Prac_NN_Topic where` を付ける
  (module ヘッダが無いと暗黙の `Main` になり、import も `ghc -fno-code` も通らない)
- **各練習ファイルが自分の `main` を持ち、それが自分のテストを走らせる。**
  テストを中央に集約しない。`make test` が `$(wildcard Prac_*.hs)` を拾い、
  `ghc -main-is Prac_NN_Topic` で各々ビルドして実行する
- テストヘルパは `TestKit.hs` を import する
- 整形は fourmolu、**インデントは 2** (`fourmolu.yaml`)。エディタ側の `shiftwidth` と揃えてある

## 作業の進め方

### コミット

- **問題のある実装でもそのままコミットして残す。** 警告が残っている、
  性能が退行している、といった理由でコミットを保留しない。本人の言葉:
  「沢山間違えてそれを記録していく」
- 代わりに**コミットメッセージに既知の問題を明記する**。
  「対応した点」と「既知の問題 (このリビジョンに残しているもの)」を分け、
  該当する issue 番号を添える (手本: `32d7a6f`)
- 論理単位ごとに分ける (ビルド設定 / ソース / ドキュメント)
- コミットは `main` に直接。ブランチを切らない

### レビューの手順

**レビューは必ずコミットを積んでから行う。** 作業ツリーを見てレビューしない。

1. レビュー対象をコミットする (動かない状態でもよい。`--no-verify` を使ったならその旨をメッセージに書く)
2. そのコミットに対してレビューし、**まず会話で伝える**
3. **会話で擦り合わせる。** 判断が要る点は選択肢を示して本人に決めてもらう
4. 合意できてから **issue に書き、対象の commit hash を明記する**
5. 同じテーマなら**1つの issue にコメントとして積み上げる**。新しい issue を毎回立てない
   (ただし積みすぎない。下記「レビュー記録は一区切りで巻き取る」)

**レビュー結果をいきなり issue に書かない。** 擦り合わせ前の指摘は的を外していることがあり
(実例: #13 でレビュー2の指摘1を後から撤回した)、確定前の内容が記録に残ると
後で読んだときに混乱する。会話で収束させてから記録する。

これは「issue への切り出しは早く」と矛盾しない。**着手前の作業項目は早く切り出し、
レビューの判断は収束させてから記録する**、という使い分け。

理由:

- レビュー対象が hash で固定されるので、後から「どの状態に対する指摘か」が確定する。
  作業ツリーはレビュー中にも動くので、指摘と実物がずれる
- issue に時系列で積むと、**同じ指摘を繰り返しているか**、
  **前回の指摘がどう解決されたか**が1画面で追える
- 会話は流れるが issue は残る。後で Discussion に起こすときの材料になる

コミットメッセージには「何を実装したか」を書き、**評価と指摘は issue 側に置く**。
役割を分けると、履歴が「やったこと」、issue が「どう見たか」で読み分けられる。

### レビュー記録は一区切りで巻き取る

積み上げは有効だが、**同じ issue に積み続けると後半で見通しが悪くなる**。
実例: #13 はレビュー9件 + 訂正3件の12コメントまで伸び、
「今どの指摘が生きているか」を知るのに全部読む必要が出た。

**対象の層が一区切りついたら、または目安として5レビューを超えたら巻き取る。**

1. 現行 issue に締めのコメントを書く。**何を扱ったか / 解決したもの / 未解決のもの**
2. 新しい issue を立て、**未解決のものだけ**を引き継ぐ。冒頭に前の issue へのリンクを置く
3. 現行 issue を close する (superseded)

こうすると、**開いている issue が常に「今生きている指摘」だけ**になる。
過去は close された issue に残り、リンクを辿れば読める。

「1つの issue に積む」と矛盾しない。**1つの期間の中では積み、期間が変わったら巻き取る**、
という使い分け。期間の切れ目は層の完成 (基底層 → 語彙層 → 文法) が自然な単位になる。

### GitHub に書くものは英語

**issue と discussion は英語で書く。** 会話・コミットメッセージ・リポジトリ内のドキュメント
(README / ADR / このスキル) は日本語のままでよい。

境界は「GitHub 上の公開面か否か」。過去に日本語で立てたものを遡って訳す必要は無い。

### 知見をどこに残すか

| 内容 | 置き場所 |
| --- | --- |
| 作業方針・規約 | このスキル |
| 構成上の決定と代償 | `docs/adr/` (ADR) |
| **設計知識・調べて分かったこと** | **GitHub Discussion** (英語) |
| 追跡したい作業・不具合 | issue (英語) |
| レビュー結果 | レビュー用 issue にコメントで積む (英語) |

設計知識を `docs/` に置かない。Discussion に上げる。

### Issue への切り出しは早く

**思いついた時点で issue に切り出す。設計が固まるのを待たない。**
「次はこれをやろう」と会話に出た時点で、本文が数行でも頭出しの issue を立てる。

- **不要になったら close すればよい。** private repository なので気兼ねは要らない。
  消せることを前提にすれば、立てる判断が軽くなる
- 会話や頭の中に置いたままだと失われる。issue にすれば後から**参照点**になり、
  Discussion に起こすときの材料にもなる
- 設計が固まったら同じ issue を書き足して育てる。最初から完成させようとしない
- やらないと決めたら理由を一行書いて close する

作業の指示や設計の骨格も、会話に書いて終わりにせず issue に切り出す
(手本: #7 が Prac_02 の骨格、#8 が Prac_03 の頭出し)。

### 問題の扱い

問題は GitHub issue に上げて追跡する。コミットを止める理由にはしない。
CI は置かない (private repository のため)。代わりに pre-commit hook が
`make fmt-check` / `make check` / `make test` を回す。

### 主張には裏を取る

性能や挙動について述べるときは**実測してから書く**。
ベンチマークは scratchpad に置き、数字を issue とコミットメッセージに残す。
「速いはず」「同じはず」で済ませない。過去にこれで
`Writer.CPS` + `[]` の O(n²) 退行を見逃しかけた。

### 設計判断の記録

非自明な構成 (`hie.yaml` の存在理由など) は `docs/adr/` に ADR として残す。
Context / Decision / Consequences / Alternatives の構成。
「支払う代償」を具体的に書くこと。
